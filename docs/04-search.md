# 04. Поиск

Файл: [`engine/src/search.rs`](../engine/src/search.rs), ~1100 строк — самый
большой модуль движка.

Основа — негамакс с alpha-beta отсечением и fail-soft семантикой. Поверх него
навешан набор техник, заимствованных из компьютерных шахмат и адаптированных под
специфику тоғызқұмалақ.

## Специфика игры и её влияние на поиск

Тоғызқұмалақ отличается от шахмат тремя свойствами, которые определили выбор
техник:

| Свойство | Значение | Следствие |
|----------|----------|-----------|
| Ветвление | 4–9 (обычно 5–8) | глубина 28–30 достижима за 3 секунды |
| Число ходов | 9 (индексы 0..8) | эвристики индексируются одним `u8` |
| Размер позиции | 24 байта, `Copy` | copy-make дешевле make/unmake |

Малое ветвление сыграло против некоторых техник. В коде явно отключены две
из них:

```rust
// Singular Extension disabled — causes node explosion in togyz kumalak
// (branching factor 5-8 means SE searches 4-7 extra subtrees per TT move)
```

```rust
// ProbCut disabled — causes recursive explosion in this game tree
```

В шахматах при ветвлении ~35 эти техники окупаются. Здесь дополнительный подпоиск
на каждый TT-ход означает пересмотр значительной доли поддерева.

## Верхний уровень: `search()`

[`search.rs:328`](../engine/src/search.rs#L328)

Порядок действий:

### 1. Тайм-менеджмент по фазе игры

Время выделяется тем щедрее, чем ближе эндшпиль ([`search.rs:334-344`](../engine/src/search.rs#L334-L344)):

```rust
self.max_time_ms = if total_board_stones <= 30 {
    time_ms * 2       // глубокий эндшпиль: двойное время
} else if total_board_stones <= 60 {
    time_ms * 3 / 2   // эндшпиль: полуторное
} else {
    time_ms
};
```

Обоснование: партия решается в эндшпиле, где цена одной ошибки максимальна.
Обратите внимание — движок может потратить **вдвое больше** запрошенного времени.

### 2. Дебютная книга

Если позиция найдена в книге, ход возвращается мгновенно с `depth: 0`
([`search.rs:346-361`](../engine/src/search.rs#L346-L361)).

### 3. Старение истории

История ходов делится пополам перед каждым поиском — чтобы значения из
предыдущих ходов партии не доминировали:

```rust
self.history[side][pit] /= 2;
```

### 4. Ранние выходы

Ноль ходов или ровно один ход — результат возвращается без поиска.

### 5. Iterative deepening + aspiration windows

С глубины 4 поиск идёт в узком окне `±20` вокруг предыдущей оценки
([`ASP_DELTA`, search.rs:39](../engine/src/search.rs#L39)). При промахе окно
удваивается; если разошлось шире 500 — полный поиск с `-INF..+INF`.

Значение `ASP_DELTA = 20` откалибровано под шкалу NNUE (деление на 64), а не под
шкалу ручной оценки.

### 6. Умный выход по времени

Два условия досрочной остановки ([`search.rs:493-514`](../engine/src/search.rs#L493-L514)):

```rust
// Стабильность лучшего хода
let stability_threshold = if total_board_stones <= 60 { 6u32 } else { 4u32 };
let time_fraction     = if total_board_stones <= 60 { 2u64 } else { 3u64 };
if best_move_stable_count >= stability_threshold
   && elapsed > self.max_time_ms / time_fraction { break; }

// Прогноз: следующая глубина займёт ~3x текущей
if elapsed * 3 > self.max_time_ms { break; }
```

В эндшпиле требуется больше подтверждений стабильности (6 вместо 4) — движок
неохотнее прекращает счёт.

## Lazy SMP

[`search_smp`, search.rs:266](../engine/src/search.rs#L266)

Простейшая схема многопоточности: N потоков ведут **одинаковый** поиск,
синхронизируясь только через общую таблицу транспозиций. Разница в скорости
потоков естественным образом рассинхронизирует их деревья, и они начинают
подсказывать друг другу через TT.

- Общая TT — `Arc<TranspositionTable>` с внутренней `UnsafeCell` (см. ниже).
- Общий флаг остановки — `Arc<AtomicBool>`, проверяется каждые 4096 узлов.
- Каждый поток получает свою копию NNUE (`nnue.clone()`) и `Arc` на EGTB.
- Дебютная книга воркерам не передаётся — она нужна только в корне.

## Основная рекурсия: `alpha_beta()`

[`search.rs:530`](../engine/src/search.rs#L530)

Порядок проверок в узле:

```
1.  Проверка времени (раз в 4096 узлов)
2.  Терминальная позиция → ±(EVAL_MATE - ply)
3.  EGTB probe → точный результат с DTM
4.  depth <= 0 → quiescence
5.  Жёсткий лимит ply (MAX_DEPTH - 4) → статическая оценка
6.  Детект повторений (история партии + путь поиска)
7.  TT probe → отсечение или ход для сортировки
8.  Razoring
9.  Reverse Futility Pruning
10. IID (если нет TT-хода в PV-узле)
11. Null Move Pruning
12. Генерация и сортировка ходов
13. Цикл по ходам: LMP, futility, LMR, extensions
14. Запись в TT
```

### Детект повторений

[`search.rs:594-611`](../engine/src/search.rs#L594-L611)

Проверяются два множества: позиции, реально сыгранные в партии
(`game_history`), и позиции на текущем пути поиска (`search_path`). Совпадение
даёт 0 — ничья.

```rust
for &h in &self.game_history {
    if h == hash { return 0; }
}
for i in 0..(ply as usize) {
    if self.search_path[i] == hash { return 0; }
}
```

Это линейный проход, но `game_history` короткая, а `ply` ограничен 64.
Именно ради `game_history` веб-сервер держит движок постоянным процессом —
иначе повторения не отслеживались бы между ходами.

### Эвристика improving

[`search.rs:650-654`](../engine/src/search.rs#L650-L654)

```rust
let improving = ply >= 2 && static_eval > self.static_evals[(ply - 2) as usize];
```

Если оценка выросла по сравнению с позицией двумя полуходами ранее, позиция
«улучшается» и отсекать надо осторожнее. Используется в RFP (margin меньше на
30) и LMR (редукция меньше на 1).

### Отсечения

| Техника | Условия | Действие |
|---------|---------|----------|
| **Razoring** | `!is_pv, depth ≤ 2, !endgame, static_eval + 150*depth < alpha` | проверка через quiescence, выход при подтверждении |
| **RFP** | `!is_pv, depth ≤ 3, !endgame, static_eval - margin ≥ beta` | вернуть `static_eval`; margin = `70*depth` (−30 при improving) |
| **NMP** | `depth ≥ 3, my_stones > 10, !endgame, ply > 0, !is_pv` | пропуск хода с редукцией `R = 2 + depth/6` |
| **Futility** | `!is_pv, depth ≤ 2, !endgame, static_eval + 80*depth < alpha` | пропуск тихих ходов кроме первого |
| **LMP** | `!is_pv, depth ≤ 3, !endgame` | пропуск тихих ходов после `LMP_TABLE[depth]` |

`LMP_TABLE = [0, 5, 8, 12, 16, 20, 24]` ([`search.rs:49`](../engine/src/search.rs#L49)).

Все отсечения **отключены в эндшпиле** (`is_endgame` — 30 камней и меньше). Это
осознанный размен: в эндшпиле точность важнее глубины.

Условие NMP `my_stones > 10` — аналог zugzwang-защиты. При малом числе камней
пропуск хода перестаёт быть заведомо невыгодным, и NMP начинает врать.

### Расширения

Два вида ([`search.rs:732-737`](../engine/src/search.rs#L732-L737) и
[`search.rs:781-789`](../engine/src/search.rs#L781-L789)):

```rust
// Эндшпильное расширение
let endgame_ext = if is_deep_endgame && ply <= 6 { 1 }
                  else if is_endgame && ply <= 2 { 1 }
                  else { 0 };

// Расширение на тұздық — аналог check extension в шахматах
if creates_tuzdyk { extension += 1; }
```

Ход, создающий тұздық, — форсирующий и меняет позицию радикально, поэтому
считается глубже.

### LMR

[`search.rs:793-810`](../engine/src/search.rs#L793-L810)

Логарифмическая формула редукции с тремя корректировками:

```rust
let mut reduction = ((depth as f32).ln() * ((i + 1) as f32).ln() / 2.5) as i32;
if is_pv    { reduction -= 1; }
if improving { reduction -= 1; }
if hist >  3000 { reduction -= 1; }
else if hist < -3000 { reduction += 1; }
reduction = reduction.clamp(1, depth - 1);
```

Сначала идёт сокращённый поиск в нулевом окне; если он превысил alpha —
пересчёт на полную глубину. В эндшпиле LMR отключён.

## Сортировка ходов

[`score_moves`, search.rs:1030](../engine/src/search.rs#L1030)

Приоритеты:

| Приоритет | Бонус | Комментарий |
|-----------|-------|-------------|
| Ход из TT | +100 000 | лучший ход из предыдущей итерации |
| Создание тұздық | +50 000 | сильнейший тактический мотив |
| Захват | +10 000 + `100 × камней` | размер добычи учитывается |
| Killer 1 / Killer 2 | +9 000 / +8 000 | по глубине |
| Countermove | +7 000 | ответ на конкретный ход соперника |
| History | значение | накопленная статистика |
| Continuation history | значение / 2 | ход как ответ на предыдущий |
| Число камней в лунке | значение | лёгкий тай-брейк |

Сортировка — селекшн-сорт, что для 4–9 элементов быстрее любого универсального
алгоритма.

Обратите внимание: `is_capture_move` ([`search.rs:1008`](../engine/src/search.rs#L1008))
считает захватом и попадание в лунку с 3 камнями (потенциальный тұздық), и
использует **приблизительный** `predict_landing`, который не учитывает пропуск
тұздық при раздаче. Для сортировки этого достаточно, но это приближение.

## Quiescence search

[`quiescence_inner`, search.rs:912](../engine/src/search.rs#L912)

Обычный quiescence рассматривает только «шумные» ходы — здесь это захваты и
создание тұздық. Но в глубоком эндшпиле поведение меняется:

```rust
let qsearch_all_moves = total_board_stones <= 15 && qs_depth < 4;
```

При 15 и менее камнях первые 4 полухода quiescence перебирает **все** ходы, а не
только захваты. Комментарий в коде объясняет: партии решаются на 45–60 камнях, и
там нужна точная тактическая картина.

EGTB опрашивается и внутри quiescence ([`search.rs:941-949`](../engine/src/search.rs#L941-L949)).

## Таблица транспозиций

Файл: [`engine/src/tt.rs`](../engine/src/tt.rs)

Запись — 24 байта: хэш, глубина, оценка, флаг границы, лучший ход, поколение.

### Потокобезопасность без блокировок

```rust
struct TTSlot(UnsafeCell<TTEntry>);
unsafe impl Send for TTSlot {}
unsafe impl Sync for TTSlot {}
```

Гонки при записи считаются **доброкачественными**: повреждённая запись будет
отброшена при проверке хэша на чтении. Это стандартный приём из Stockfish,
явно отмеченный в комментарии кода. Формально это UB по правилам Rust, но
практически работает на всех целевых архитектурах.

### Стратегия замещения

[`store`, tt.rs:108](../engine/src/tt.rs#L108)

```rust
let should_replace = entry.depth < 0          // слот пуст
    || entry.hash == hash                     // та же позиция
    || entry.generation != gen                // запись из прошлого поиска
    || depth >= entry.depth;                  // не мельче существующей
```

Depth-preferred с учётом возраста. Поколение увеличивается в начале каждого
поиска из корня (`new_search()`).

Размер по умолчанию — 64 МБ ([`Searcher::new(64)`](../engine/src/main.rs#L159)),
округляется вниз до степени двойки.

## Zobrist-хэширование

Файл: [`engine/src/zobrist.rs`](../engine/src/zobrist.rs)

Ключи генерируются детерминированным xorshift64 с фиксированным сидом
`0x12345678_DEADBEEF` — хэши воспроизводимы между запусками.

Компоненты хэша:

| Компонент | Размер таблицы |
|-----------|----------------|
| `pits[side][pit][stones]` | 2 × 9 × 33 |
| `kazan[side][value]` | 2 × 163 |
| `tuzdyk[side][pos+1]` | 2 × 10 |
| `side_to_move` | 1 |

**Важное ограничение**: количество камней квантуется в бакеты 0..32
([`MAX_STONES_BUCKET = 32`](../engine/src/zobrist.rs#L11)). Позиции, отличающиеся
только тем, что в лунке 33 или 40 камней, дают **одинаковый хэш**. Такие лунки
редки, но возможны — например, при накоплении в одной лунке в затяжной партии.
Последствие — ложное срабатывание TT или ложный детект повторения.

Инкрементального обновления хэша нет: `hash()` каждый раз считает всё с нуля
(18 лунок + 2 қазана + 2 тұздық + сторона = 23 XOR). При copy-make это
приемлемо, но остаётся местом для оптимизации.

## Наблюдаемая производительность

По отчётам: глубина **28–30** за 3 секунды. В [`REPORT.md`](../REPORT.md) отмечено,
что для чемпионского уровня, вероятно, нужно 35+.

Вывод строки `info` идёт в **stderr**, а не stdout — это важно для протокола
`serve`, где stdout зарезервирован под ответы:

```
info depth 24 score 142 nodes 8451203 nps 2817067 time 3000 pv pit7
```
