# 05. Оценочная функция

В движке две оценки: ручная (HCE, [`engine/src/eval.rs`](../engine/src/eval.rs)) и
нейросетевая (NNUE, [06-nnue.md](06-nnue.md)). Какая применяется — решает
[`Searcher::eval()`](../engine/src/search.rs#L166).

Оценка всегда даётся **с точки зрения стороны, которая ходит**: положительное
значение — хорошо для неё.

## Как выбирается оценка

[`search.rs:166-214`](../engine/src/search.rs#L166-L214)

```rust
fn eval(&self, board: &Board) -> i32 {
    if let Some(ref nnue) = self.nnue {
        let base = nnue.evaluate(board) / 64;
        if total <= 60 {
            base + mobility_bonus + starvation + finish_bonus + kazan_bonus
        } else {
            base
        }
    } else {
        evaluate(board)   // HCE
    }
}
```

То есть: **если веса NNUE загрузились — HCE в поиске не участвует вообще**. Она
остаётся запасным вариантом и основой для Texel-тюнинга.

> **Расхождение с отчётом.** [`REPORT.md`, раздел 4.3](../REPORT.md) описывает
> гибридную формулу смешивания NNUE и HCE по фазам:
> `(nnue + hce*3)/4` при ≤15 камнях и `(nnue + hce)/2` при ≤30. **В текущем коде
> этой формулы нет.** Вместо смешивания реализованы отдельные эндшпильные
> добавки к NNUE (описаны ниже). Отчёт описывает более раннюю версию.

## Эндшпильные добавки к NNUE

Активируются при 60 и менее камнях на доске. Все масштабируются общим
коэффициентом ([`search.rs:183-184`](../engine/src/search.rs#L183-L184)):

```rust
let scale = ((65 - total as i32).max(1)) / 15;
let scale = scale.clamp(1, 4);
```

| Камней на доске | `scale` |
|-----------------|---------|
| 60 | 1 |
| 30 | 2 |
| 15 | 3 |
| 5 | 4 |

| Добавка | Формула | Смысл |
|---------|---------|-------|
| Мобильность | `(my_active − opp_active) × 3 × scale` | число непустых лунок |
| Starvation | `(21 − opp_stones)² × scale / 8` при `opp_stones ≤ 20` | квадратичное давление |
| Finishing | `(9 − opp_stones) × 8 × scale` при перевесе >5 и `opp_stones ≤ 8` | добить соперника |
| Близость к 82 | `(my_kazan − 65) × 2 × scale` при `my_kazan ≥ 65` | ускорение к победе |

Эти добавки компенсируют слабость NNUE в эндшпиле: сеть обучалась на self-play
данных, где эндшпильных позиций относительно мало, и не выучила стратегию
истощения.

## Ручная оценка (HCE)

[`evaluate()`, eval.rs:28](../engine/src/eval.rs#L28)

### Веса

[`eval.rs:9-21`](../engine/src/eval.rs#L9-L21)

```rust
const MATERIAL_WEIGHT: i32 = 21;
const TUZDYK_VALUE: [i32; 9] = [350, 420, 400, 450, 550, 530, 560, 380, 0];
const THREAT_WEIGHT: i32 = 11;
const PIT_STONES_WEIGHT: i32 = 3;
const MOBILITY_WEIGHT: i32 = 124;        // самый важный позиционный фактор
const EMPTY_PIT_PENALTY: i32 = -5;
const LARGE_PIT_BONUS: i32 = 1;
const ENDGAME_MATERIAL_BOOST: i32 = -6;
const CAPTURE_OPP_WEIGHT: i32 = 4;
const STARVATION_WEIGHT: i32 = 15;
const STARVATION_FINISH: i32 = 200;
```

Два числа заслуживают отдельного внимания.

**`MOBILITY_WEIGHT = 124` против `MATERIAL_WEIGHT = 21`.** Мобильность весит в
шесть раз больше материала — и это для игры, где цель буквально «набрать больше
камней». Значение получено Texel-тюнингом, а не подобрано вручную. Интерпретация:
камни в қазане уже никуда не денутся, а вот количество доступных ходов
определяет, сможете ли вы их набирать дальше и не окажетесь ли в позиции, где
любой ход отдаёт материал.

**`TUZDYK_VALUE` — позиционный, а не константный.** Значения получены из анализа
винрейта в 533 тысячах партий PlayOK и записаны в комментарии кода:

| Лунка | Винрейт | Вес |
|-------|---------|-----|
| 7 | 62.2% | 560 |
| 5 | 60.1% | 550 |
| 6 | 58.5% | 530 |
| 4 | 55.2% | 450 |
| 2 | 53.1% | 420 |
| 3 | 52.0% | 400 |
| 8 | 51.5% | 380 |
| 1 | 50.3% | 350 |
| 9 | — | 0 (запрещено правилами) |

Тұздық в 7-й лунке почти вдвое ценнее тұздық в 1-й. Причина — позиция в цикле
раздачи: через средние и правые лунки соперника проходит больше камней.

### Starvation — почему квадратично

```rust
if opp_pit_stones <= 9 {
    let pressure = 10 - opp_pit_stones;
    score += pressure * pressure * STARVATION_WEIGHT;
}
```

При 9 камнях у соперника бонус равен `1² × 15 = 15`. При 1 камне —
`9² × 15 = 1215`. Разница в 80 раз. Это отражает правило: когда у стороны
кончаются камни, партия останавливается, и выигрывает тот, кто впереди по
қазану. Последний отобранный камень стоит несоизмеримо дороже первого.

### Finishing bonus

```rust
if material_diff > 5 && opp_pit_stones <= 3 {
    score += (4 - opp_pit_stones) * STARVATION_FINISH;   // до 600
}
```

Решает конкретную проблему: движок, выигрывающий по материалу, при соперничестве
других факторов мог «вернуть» камни на сторону соперника вместо того, чтобы
завершить партию. Бонус до 600 пунктов делает добивание безальтернативным.

### Миттельшпильная позиционка

Активна строго на полуходах 30–60 ([`eval.rs:175`](../engine/src/eval.rs#L175)):

| Фактор | Вес |
|--------|-----|
| Масса камней на своей стороне | ×2 |
| Тяжёлые лунки (10+ камней) | ±5 за лунку |
| Штраф за раздробленность (5+ лунок с 1–2 камнями) | −10 за лунку сверх 4 |
| Правые лунки (7–9) | ×2 |

Раздробленная позиция — много лунок с одним-двумя камнями — плохо тем, что из
неё почти невозможно организовать захват: короткие раздачи не доходят до
стороны соперника.

### Мат-оценки

```rust
pub const EVAL_INF: i32 = 100_000;
pub const EVAL_MATE: i32 = 90_000;
```

Победа даёт `EVAL_MATE − move_count`, поражение — `−EVAL_MATE + move_count`.
Вычитание счётчика ходов заставляет движок предпочитать **быстрые** победы и
**медленные** поражения.

## Texel-тюнинг

Файл: [`engine/src/texel.rs`](../engine/src/texel.rs) (423 строки),
запуск: `./togyzkumalaq-engine texel`

Классический метод подбора весов оценки: веса подгоняются так, чтобы оценка,
пропущенная через сигмоиду, лучше всего предсказывала фактический результат
партии. Тюнинг проводился на 77 тысячах позиций из партий PlayOK и, по
[`REPORT.md`](../REPORT.md), дал **44% сокращения ошибки**.

Именно отсюда взялись контринтуитивные значения вроде `MOBILITY_WEIGHT = 124` и
`ENDGAME_MATERIAL_BOOST = -6` (отрицательный — то есть в эндшпиле важность
материала слегка **снижается**, потому что его начинают перевешивать
позиционные факторы).

## Вспомогательная функция `predict_landing`

[`eval.rs:217`](../engine/src/eval.rs#L217) и дубль в
[`search.rs:241`](../engine/src/search.rs#L241)

Обе версии предсказывают, куда упадёт последний камень, и обе **игнорируют
пропуск тұздық** при раздаче — о чём честно сказано в комментарии:

```rust
/// Predict where the last stone lands (approximate — doesn't account for tuzdyk skipping)
```

Когда на пути раздачи есть тұздық, камни в него уходят в қазан, и фактическая
точка приземления сдвигается. Для сортировки ходов и оценки возможностей захвата
погрешность допустима — но это приближение, а не расчёт. Функция продублирована
в двух модулях с немного разной обработкой переносов.
