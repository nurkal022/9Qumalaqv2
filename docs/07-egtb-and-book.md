# Эндшпильные таблицы (EGTB)

Файл: [`engine/src/egtb.rs`](../engine/src/egtb.rs) (785 строк)
Артефакт: `engine/egtb.bin` (~68 МБ, **не в репозитории**)

## Почему это вообще возможно

Ключевое свойство игры, сформулированное в комментарии к модулю:

```rust
/// Key insight: total board stones never increase after a move
/// (captures/tuzdyk drain stones to kazan), enabling bottom-up solving.
```

Число камней на доске **монотонно не возрастает**: раздача камни только
перемещает, а захваты и тұздық уводят их в қазан безвозвратно. Значит, множество
позиций с N камнями замкнуто относительно перехода «вниз» — из позиции с N
камней можно попасть только в позицию с N или меньше.

Это позволяет решать снизу вверх: сначала N = 0, потом N = 1, и так далее. При
решении уровня N все достижимые позиции уровня < N уже известны точно.

В шахматах аналогичное свойство даёт число фигур, и на нём построены таблицы
Налимова и Syzygy.

## Формат записи

Одна позиция — **один байт** ([`egtb.rs:24-47`](../engine/src/egtb.rs#L24-L47)):

```
биты [7:6] — результат: 1 = Win, 2 = Draw, 3 = Loss
биты [5:0] — DTM (distance to mate), 0–63
```

Результат даётся с точки зрения ходящей стороны.

## Кодирование позиции

[`encode_position`, egtb.rs:50](../engine/src/egtb.rs#L50)

Позиция упаковывается в `u128`:

| Поле | Бит | Размер |
|------|-----|--------|
| 18 лунок | 0–71 | по 4 бита (0–15 камней) |
| `kazan[0]` | 72–79 | 8 бит |
| `kazan[1]` | 80–87 | 8 бит |
| `tuzdyk[0]` | 88–91 | 4 бита (0 = нет, 1–9 = позиция+1) |
| `tuzdyk[1]` | 92–95 | 4 бита |
| `side_to_move` | 96 | 1 бит |

По 4 бита на лунку — то есть **максимум 15 камней в лунке**. Для эндшпиля с
N ≤ 4 это заведомо достаточно, но кодирование не универсально: расширить таблицы
на большие N без смены формата не получится.

## Файл на диске

```
[8 байт]  магия "TKEGTB01"
[4 байта] max_stones (u32, LE)
[4 байта] num_entries (u32, LE)
[повтор]  key: u128 (16 байт) + value: u8 (1 байт)
```

Записи отсортированы по ключу — поиск бинарный
([`probe`, egtb.rs:145](../engine/src/egtb.rs#L145)):

```rust
pub fn probe(&self, board: &Board) -> Option<EgtbEntry> {
    if board.total_board_stones() as u32 > self.max_stones { return None; }
    let key = encode_position(board);
    match self.keys.binary_search(&key) {
        Ok(idx) => EgtbEntry::unpack(self.values[idx]),
        Err(_) => None,
    }
}
```

Первая проверка — по числу камней, она отсекает подавляющее большинство
обращений без всякого поиска. Это важно, потому что probe вызывается в **каждом**
узле alpha-beta ([`search.rs:568`](../engine/src/search.rs#L568)) и quiescence
([`search.rs:941`](../engine/src/search.rs#L941)).

Данные хранятся в двух параллельных векторах (`keys: Vec<u128>` и
`values: Vec<u8>`), а не в векторе пар — это уплотняет ключи в кэше при бинарном
поиске.

## Генерация

[`generate_egtb`, egtb.rs:253](../engine/src/egtb.rs#L253)

```bash
cd engine
./target/release/togyzkumalaq-engine egtb-gen 4 egtb.bin
```

Для каждого N перебираются:

1. Все распределения N камней по 18 лункам
   ([`enumerate_pit_distributions`](../engine/src/egtb.rs#L204)).
2. Все допустимые разбиения `162 − N` камней между двумя қазанами.
3. Все комбинации тұздық (включая «нет») с проверкой ограничений правил.
4. Обе стороны хода.

Затем ретроградный анализ: терминальные позиции размечаются напрямую, остальные
решаются через уже решённых потомков ([`try_solve`](../engine/src/egtb.rs#L474)).

Для N ≤ 4 получается около **170 млн позиций**.

[`verify_egtb`, egtb.rs:577](../engine/src/egtb.rs#L577) берёт случайные позиции

## Использование в поиске

При попадании в таблицу поиск сразу возвращает точный результат с учётом
расстояния до конца:

```rust
EgtbResult::Win  => EVAL_MATE - ply - entry.dtm as i32,
EgtbResult::Loss => -EVAL_MATE + ply + entry.dtm as i32,
EgtbResult::Draw => 0,
```

Учёт DTM заставляет движок выбирать **кратчайший** путь к выигрышу и
**длиннейший** к проигрышу.

Таблица передаётся воркерам SMP через `Arc` — одна копия на все потоки
([`search.rs:280`](../engine/src/search.rs#L280)).

Вклад по отчётам: **~30 Elo**.

# Дебютная книга

В проекте **две независимые книги** в разных форматах, которые не
синхронизированы между собой.

## Книга движка

Файл: [`engine/src/book.rs`](../engine/src/book.rs)
Артефакт: [`engine/opening_book.txt`](../engine/opening_book.txt) — 21 016 строк

Текстовый формат, поля разделены `|`:

```
пит_белых|пит_чёрных|қазаны|тұздық|сторона|лучший_ход|число_партий
```

Пример реальной строки:

```
11,11,11,11,11,2,0,12,11|11,11,11,11,11,1,9,1,2|10,4|-1,-1|0|0|26531
```

Последнее поле — сколько партий прошло через эту позицию. Здесь 26 531, что
говорит о том, что книга строилась на очень большой выборке.

### Поиск в книге

[`lookup`, book.rs:75](../engine/src/book.rs#L75)

Реализация — **линейный перебор всех записей** с полным сравнением позиции:

```rust
for entry in &self.entries {
    if entry.side_to_move != stm { continue; }
    if entry.pits[0] != board.pits[0] || entry.pits[1] != board.pits[1] { continue; }
    ...
    return Some(entry.best_move as usize);
}
```

При 21 тысяче записей это до 21 000 сравнений на обращение. Спасает только то,
что книга опрашивается **один раз в корне поиска**
([`search.rs:347`](../engine/src/search.rs#L347)), а не в каждом узле. Тем не
менее, хэш-таблица здесь была бы уместнее — см.
[13-known-issues.md](13-known-issues.md#5-линейный-поиск-в-дебютной-книге).

Рядом лежит [`opening_book.bin`](../engine/opening_book.bin) (9.3 КБ) — судя по
всему, артефакт другого формата; код [`book.rs`](../engine/src/book.rs) читает
только текстовую версию.

## Книга веб-сервера

Файл: [`web/opening_book.json`](../web/opening_book.json) (236 КБ)
Генератор: [`web/generate_book.py`](../web/generate_book.py)

Формат — JSON со статистикой по каждому ходу:

```json
{
  "positions": {
    "<позиция-строкой>": {
      "total": 42,
      "moves": {
        "6": { "count": 20, "wins": 12, "draws": 3 }
      }
    }
  }
}
```

### Отличие: вероятностный выбор

Движок берёт из книги один заранее записанный лучший ход. Сервер выбирает
**случайно с весами** ([`server.py:104-118`](../web/server.py#L104-L118)):

```python
win_rate = (wins + draws * 0.5) / max(count, 1)
weight = count * (0.3 + win_rate)
```

Вес пропорционален частоте хода, умноженной на его успешность со смещением 0.3.
Смещение гарантирует, что даже ход с нулевым винрейтом сохраняет шанс быть
выбранным, если он часто встречался. Это делает игру движка **разнообразной** —
он не повторяет один и тот же дебют партия за партией.

Фильтры при генерации ([`generate_book.py:16-17`](../web/generate_book.py#L16-L17)):

```python
MIN_GAMES = 3     # минимум партий на позицию
MIN_ELO   = 1600  # минимальный рейтинг хотя бы одного из игроков
```

Дополнительно при выборе отбрасываются ходы, встретившиеся менее 2 раз, и
позиции с менее чем 3 партиями ([`server.py:97`](../web/server.py#L97),
[`server.py:110`](../web/server.py#L110)).

### Приоритет книги на сервере

Сервер опрашивает книгу **до** обращения к движку
([`server.py:147-158`](../web/server.py#L147-L158)) и возвращает ход мгновенно,
с `depth: 0, nodes: 0`. Клиент может отключить это, передав `use_book: false`.

Скрипты генерации книги для движка:
[`gen_opening_book.py`](../engine/gen_opening_book.py) и
[`gen_opening_book_v2.py`](../engine/gen_opening_book_v2.py).

## Ограничение обеих книг

По [`REPORT.md`](../REPORT.md) книга покрывает около 16 полуходов. Для дебютной
теории тоғызқұмалақ это немного — отмечено в отчёте как одна из известных
слабостей движка.
