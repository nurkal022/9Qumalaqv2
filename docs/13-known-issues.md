## 1. Секреты в репозитории

**Критично. Требует действий, а не правки кода.**

[`deploy.py:7-9`](../deploy.py#L7-L9):

```python
HOST = '5.129.198.203'
USER = 'root'
PASS = 'REDACTED'
```

Root-пароль от боевого сервера в открытом виде.

Пароль присутствует **в истории коммитов** — он попал туда в `bb1ced9` и
`ec5bdf8`. Репозиторий имеет удалённый origin на GitHub
(`github.com/nurkal022/9Qumalaqv2.git`), и коммиты запушены.

Удаление строки из файла проблему **не решает** — старые коммиты остаются
доступны.

Порядок действий:

1. **Сменить пароль на сервере немедленно.** Это первое и обязательное действие;
   всё остальное — уборка.
2. Перейти на SSH-ключи, отключить парольную аутентификацию root
   (`PermitRootLogin prohibit-password` в `sshd_config`).
3. Переписать `deploy.py` на чтение из окружения:
   ```python
   HOST = os.environ['DEPLOY_HOST']
   USER = os.environ.get('DEPLOY_USER', 'root')
   ```
4. Опционально — вычистить историю (`git filter-repo`, BFG) и форсированно
   перезаписать удалённые ветки. Это ломает клоны у всех, кто их имеет, поэтому
   решение принимается отдельно. Смену пароля откладывать до этого нельзя.

Проверить остальные скрипты деплоя на такие же вставки:
[`deploy.sh`](../alphazero-code/deploy.sh),
[`setup_server.sh`](../alphazero-code/setup_server.sh),
[`upload_files.sh`](../alphazero-code/upload_files.sh).

## 2. `unmake_move` не откатывает тұздық

**Латентный баг — сейчас не проявляется, но сработает при изменении кода.**

[`board.rs:118-131`](../engine/src/board.rs#L118-L131):

```rust
let undo = UndoInfo {         // ← не mut
    pit_index,
    stones_picked: self.pits[me][pit_index],
    captured: 0,
    tuzdyk_created: -1,       // ← ставится один раз и никогда не меняется
    ...
};
```

При создании тұздық ([`board.rs:189-193`](../engine/src/board.rs#L189-L193))
поле `undo.tuzdyk_created` не обновляется — переменная объявлена без `mut` и
физически не может быть изменена.

Следствие: проверка в [`board.rs:213`](../engine/src/board.rs#L213) — мёртвый код:

```rust
if undo.tuzdyk_created >= 0 {   // всегда false
    self.tuzdyk[me] = -1;
}
```

**Тұздық после отката хода не снимается.**

### Почему не проявляется сейчас

Поиск использует copy-make, а не make/unmake
([`search.rs:775-776`](../engine/src/search.rs#L775-L776)):

```rust
let mut new_board = *board;
let _undo = new_board.make_move(m);   // undo игнорируется
```

`Board` реализует `Copy` и весит 24 байта — копирование дешевле восстановления.
Поэтому `unmake_move` вызывается только при откате хода в интерактивной игре.

Тест [`test_make_unmake_preserves_state`](../engine/src/board.rs#L384) проходит
потому, что проверяет ход с 7-й лунки, который тұздық не создаёт.

### Исправление

```rust
let mut undo = UndoInfo { ... };
// ...
if count == 3 && self.can_create_tuzdyk(me, current_pit) {
    self.tuzdyk[me] = current_pit as i8;
    undo.tuzdyk_created = current_pit as i8;   // ← добавить
    ...
}
```

И добавить тест, где ход создаёт тұздық, а затем откатывается.

Альтернатива — удалить `unmake_move` и `UndoInfo` совсем, раз поиск ими не
пользуется. Мёртвый API, который «почти работает», опаснее отсутствующего.

## 3. Правила игры реализованы трижды

**Архитектурный риск.**

| Реализация | Файл | Кто использует |
|------------|------|----------------|
| Rust | [`engine/src/board.rs`](../engine/src/board.rs) | движок, EGTB, datagen |
| Python | [`alphazero-code/alphazero/game.py`](../alphazero-code/alphazero/game.py) | обучение AlphaZero |
| JavaScript | [`alphazero-code/game.js`](../alphazero-code/game.js) | браузерный AI |
| JavaScript (ещё раз) | [`web/index.html`](../web/index.html#L768) | отрисовка и валидация |

Фактически **четыре** реализации: `web/index.html` содержит свои `makeMove`,
`isValidMove`, `getGameResult`.

Кросс-проверки между ними нет. [`validate_perft.py`](../validate_perft.py)
проверяет только Rust.

Последствия расхождения: сеть AlphaZero обучится на неверных правилах;
браузер и сервер разойдутся в оценке позиции; невоспроизводимые баги в
интерфейсе.

### Что можно сделать

Минимум — тест соответствия: прогнать N случайных партий через все реализации и
сверить последовательности позиций. Достаточно одного скрипта, вызывающего
`togyzkumalaq-engine perft` и его аналоги на Python/JS.

Радикально — собрать Rust в WebAssembly и использовать одну реализацию везде.
Движок не имеет зависимостей, что делает это реалистичным.

## 4. Коллизии Zobrist при 33+ камнях в лунке

[`zobrist.rs:11`](../engine/src/zobrist.rs#L11):

```rust
const MAX_STONES_BUCKET: usize = 32;
```

```rust
let bucket = stones.min(MAX_STONES_BUCKET);
h ^= self.pit_keys[side][pit][bucket];
```

Позиции, отличающиеся только тем, что в лунке 33 или, скажем, 45 камней, дают
**одинаковый хэш**.

Такие лунки редки, но возможны: в затяжной партии камни концентрируются, и 40+
в одной лунке встречается. Последствия — ложное срабатывание TT (вернётся оценка
другой позиции) или ложный детект повторения (партия объявляется ничьей, хотя
позиция другая).

Исправление тривиально — увеличить бакет до 64 или 82. Таблица ключей вырастет с
2×9×33 до 2×9×83 значений `u64`, то есть с 4.7 КБ до 12 КБ. Ничтожная цена.

## 5. Линейный поиск в дебютной книге

[`book.rs:75-93`](../engine/src/book.rs#L75-L93)

```rust
for entry in &self.entries {
    if entry.side_to_move != stm { continue; }
    if entry.pits[0] != board.pits[0] || entry.pits[1] != board.pits[1] { continue; }
    ...
}
```

При 21 016 записях это до 21 тысячи полных сравнений позиции на каждое обращение.

Смягчающее обстоятельство: книга опрашивается один раз в корне поиска
([`search.rs:347`](../engine/src/search.rs#L347)), а не в узлах. При 3 секундах
на ход накладные расходы теряются в шуме.

Но структура данных выбрана неверно. Замена на `HashMap<u64, u8>` по
Zobrist-хэшу позиции — примерно двадцать строк кода, и поиск станет O(1). Хэш уже
считается в движке.

Рядом лежит [`opening_book.bin`](../engine/opening_book.bin) (9.3 КБ) — судя по
всему, артефакт какого-то бинарного формата, но [`book.rs`](../engine/src/book.rs)
читает только текстовую версию. Стоит выяснить, нужен ли он вообще.

## 6. Отчёты разошлись с кодом

[`REPORT.md`, раздел 4.3](../REPORT.md) описывает гибридную формулу смешивания
NNUE и HCE по фазам партии:

```rust
if total_board_stones <= 15 {
    (nnue_score + hce_score * 3) / 4
} else if total_board_stones <= 30 {
    (nnue_score + hce_score) / 2
} else {
    nnue_score
}
```

**В текущем коде этой формулы нет.** [`search.rs:166-214`](../engine/src/search.rs#L166-L214)
реализует другой подход: NNUE плюс набор явных эндшпильных добавок
(мобильность, starvation, finishing, близость к 82), причём порог активации — 60
камней, а не 30.

Отчёт описывает более раннюю версию движка. При этом гибрид NNUE+HCE назван в
отчёте «главным прорывом» (+285 Elo), так что расхождение существенное — неясно,
осознанно ли формула была заменена и не потерялись ли при этом Elo.

Стоит зафиксировать актуальное состояние в отчёте либо пометить раздел 4.3 как
исторический.

## 7. Приблизительный `predict_landing`

Функция продублирована в двух местах — [`eval.rs:217`](../engine/src/eval.rs#L217)
и [`search.rs:241`](../engine/src/search.rs#L241) — и обе версии игнорируют
пропуск тұздық при раздаче, о чём честно сказано в комментарии:

```rust
/// Predict where the last stone lands (approximate — doesn't account for tuzdyk skipping)
```

Когда на пути раздачи стоит тұздық, камни в него уходят в қазан, и фактическая
точка приземления сдвигается назад. Ошибка растёт с числом раздаваемых камней.

Влияние: неточная сортировка ходов (`score_moves`), неточный подсчёт
возможностей захвата в HCE, неточный отбор ходов в quiescence
(`is_capture_move`). На корректность это не влияет — только на качество
эвристик.

Обе копии стоит объединить в одну функцию и учесть тұздық. Ошибка сортировки
ходов напрямую бьёт по эффективности alpha-beta.

## 8. Копия NNUE на каждый поток

[`search.rs:279`](../engine/src/search.rs#L279):

```rust
let nnue = self.nnue.clone();
```

При 8 потоках — 8 копий весов в памяти. Для 37 КБ несущественно, но EGTB уже
раздаётся через `Arc`, а NNUE — нет. Непоследовательно, и при переходе на более
крупную сеть станет проблемой.

Сеть в поиске только читается — `Arc<NnueNetwork>` подошёл бы без изменений
логики.

## 9. Очистка истории при откате хода

[`web/index.html:1147-1165`](../web/index.html#L1147-L1165)

`undoMove()` снимает два полухода, пересчитывает доску с начала и вызывает
`/api/newgame`. Последнее **полностью очищает историю партии в движке**, но не
восстанавливает её для оставшихся ходов.

После любого отката движок перестаёт видеть повторения на предыдущих позициях до
конца партии. Влияние на силу небольшое, но поведение неочевидное.

Исправление: после `newgame` переиграть оставшиеся позиции через `/api/position`.

## 10. Мелкие расхождения и мусор

**`flask-cors` в requirements без применения.** README предлагает ставить
зависимости веб-демо командой `pip install -r alphazero-code/requirements.txt`,
где указан `flask-cors==4.0.0`. Но [`web/server.py`](../web/server.py) CORS не
подключает. Нужен он только для [`alphazero-code/server.py`](../alphazero-code/server.py).

**Дублированные файлы партий.** `mugalim (1..5).txt` — пять байт-в-байт
одинаковых копий, `argenby.txt` и `argenby (1).txt` — тоже. Это не влияет на
обучение: [`parse_games.py:158-161`](../parse_games.py#L158-L161) дедуплицирует
партии по отпечатку из имён игроков и первых 20 ходов. Но 800 КБ мусора в дереве
и путаница при ручном просмотре остаются. Каталог `gameNew2/` при этом указан в
[`.gitignore`](../.gitignore), хотя файлы в репозитории присутствуют — то есть
были закоммичены до добавления правила.

**`unsafe impl Send/Sync` для TT.** [`tt.rs:44-45`](../engine/src/tt.rs#L44-L45) —
формально UB по правилам Rust (гонки данных на `UnsafeCell` без атомиков).
Практически это стандартный приём Stockfish, работающий на всех целевых
архитектурах, и комментарий в коде это признаёт явно. Оставлено как есть
осознанно; отмечено здесь, чтобы не выглядело недосмотром.

**Дублирование правил внутри `web/index.html`.** Файл на 39 КБ содержит вёрстку,
стили, игровую логику и сетевой слой. Разделение на модули упростило бы
поддержку, но это вопрос вкуса, а не корректности.
