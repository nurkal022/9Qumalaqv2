**Как читать вердикты.**
- **подтверждено**: есть первичный файл, n достаточно, нет известного бага.
- **слабое**: мало партий, один сид или эффект в пределах шума.
- **in-lineage**: мерили против своей же линейки. По `docs/MEASUREMENT_PROTOCOL.md` это проверка на регрессию, а не сила.
- **испорчено**: на результат влияет баг правил, разметки или харнесса.
- **противоречит**: другие данные говорят обратное.
- **нет доказательств**: лога не нашлось, есть только текст отчёта.

Что считается первичным источником: лог, jsonl партий или чекпоинт на диске. Отчёты и память
агента (`~/.claude/projects/-home-nurlykhan-9QumalaqV2/memory/*.md`) — вторичные источники.
Сентябрьская сессия 26–27.09 сама провела аудит и многое нашла, но её скрипты в `/tmp` стёрла
перезагрузка. Её цифры (MCTS batch-1, «value запомнила партии» и т.п.) здесь помечены как

Значит, outcome-метки self-play эры 0 в эндшпиле описывают другую игру.
2. **Баг эры 1, исправленный 12.09, сам по себе не объясняет «стену value» июня.** В человеческих партиях он портит около 1% меток. В партиях движок-движок:
   - 84.5% партий кончаются на «самоопустошении» (169/200), то есть в позиции, которая по реальному правилу не терминальна;
   - лишь в 5.5% (11/200) соперник по реальному правилу продолжил бы игру, и исход мог бы измениться.

   Это шум порядка 5%, а не 30–50%. Настоящая причина «стены» — сломанные измерения, см. п. 3.
3. **Почти все выводы про MCTS/AlphaZero стоят на измерениях, которые не меряли MCTS.**
   - Python Gumbel AZ (март–апрель, «0:20») делает поиск в один ход: каждая «симуляция» заново оценивает того же ребёнка сетью (`gumbel_az.py:128-156`), дерева нет.
   - Rust `mcts --eval` до 18.06 возвращал терминальные значения с обратным знаком (`mcts.rs:262`).
   - После 18.06 `best_move_deep` собирает по `virtual_batch = min(sims, 64)` листьев (`eval_vs_engine.rs:70`). При 200 симуляциях это 3–4 обновления, и игра почти повторяет prior (вторичный источник: 91–97% совпадений).
   - Гейты были по 16–48 партий из **стартовой позиции, без дебютного набора** (`play_eval_game` начинает с `Board::new()`, сеть играет argmax, движок берёт ходы из книги). Одна и та же `sup1500` дала 43.8% в одном замере и 28.1% (9/32) в `runs/sp_sup1500/run.log`.
4. **Весь вывод фазы A «оценка лучше, силы нет» опровергнут.**
   - Скрипт 9qum засчитывал поражение, когда наш движок старого правила отвечал «terminal». Я заново оценил логи по финальному `tfen` (`regrade_9qum.py`).
   - Окно 1: acc256 — 7 «поражений» в незаконченных партиях, исправленный счёт до **41.7%** против 12.5% у production в том же окне.
   - Окно 2: v4 — 7 таких партий, до 45.8%, против 29.2% у production.
5. **Сентябрьская `mix1` — единственный кандидат с положительным внешним парным замером.**
   - 9/22 = 40.9% против 2/22 у production на тех же дебютах и местах. Парная разница +31.8 п.п., t=2.6, 95% ДИ [+8, +56] п.п.
   - Но production в этом окне играл **без EGTB** (TKEGTB02 не грузится старым бинарём), в 2 потока и 1000 мс.
   - Тот же production-net в окне 12.09 (24 потока, 1.8 с, со своей EGTB) набрал 39.6%. Значит, против полноценного production выигрыш mix1 пока не доказан.
6. **«Ширина 1024 вредна» — частично артефакт learning rate.**
   - Я переобучил mix2 при ширине 1024 с меньшим LR. Val loss 0.4990 при lr 2e-3 становится 0.3910 при lr 5e-4, это равно acc256 при lr 2e-3 (0.3903).
   - Trainer использует один AdamW-LR для всех ширин.
   - Стоимость по NPS реальна, но вывод «1024 хуже по качеству» неверен.
7. **Ранние «законы» NNUE не доказаны.**
   - Batch 258 Elo, K +256 Elo, λ≈300 Elo, «больше данных хуже» опираются на 50–100 партий против HCE и один сид, в эре 0.
   - Сравнение по batch смешано с платформой (Mac против GPU). Два запуска с одинаковым конфигом (B и M) дали val loss 0.0454 и 0.0679.
   - Разброс между сидами при K=400 (72.5–96.8%) больше самого эффекта K.
8. **«PlayOK бесполезен для NNUE» — методологическая ошибка.** Сравнивали val loss целей разной природы: бинарный исход против sigmoid(eval). Матчем это не проверяли ни разу. Позже PlayOK-исходы дали +104 Elo (Gen3) и вошли в лучший кандидат `mix1`.
9. **«58 признаков = шум» испорчено.** Признаки 40, 41, 48, 49 Python делит на 50, а Rust на 81 (`train_nnue_v2.py:92,100` против `nnue.rs:835,859`). Сеть учили на одном масштабе, а играла она на другом, в 1.62 раза меньшем.

**Перспективный путь к 2500+** (подробно в §7). Работать нужно в первую очередь над функцией оценки, обученной на **исходах по реальному правилу** при **сплите по партиям**. Обязательное условие — честные парные внешние гейты на 200+ партий. Порядок:
- Сразу: NNUE v2 (sparse) плюс итеративная разметка исходами. Это единственный рычаг, который хоть раз дал внешний плюс.
- Параллельно: AlphaZero с исправленным харнессом на сервере. Метод в этой игре ни разу честно не проверялся, а все известные сильные программы (9qum, PlayOK `mcts` ≈2510) — семейство MCTS/AZ.

## 6. Гипотезы, отброшенные, возможно, зря: кандидаты на перепроверку

Отсортировано по соотношению «ожидаемая польза / стоимость». Все повторы делать по реальному правилу, с дебютным набором и 200+ парными партиями.

1. **MCTS/AlphaZero как метод.** Отброшен по 0:20 (поиск в один ход, эра 0), по «поиск вредит» (vb64) и по знаковому багу до 18.06. Ни один из этих замеров не мерил MCTS. Перепроверка:
   - `best_move_deep` с `virtual_batch` 1 и 8 при 200 и 800 sims для `sup1500` против движка на фиксированной глубине 8;
   - 100 дебютов ×2 цвета;
   - порт правила эры 2 в `core` ветки alphazero.

   Около часа GPU. Это самая дешёвая и самая важная проверка: она восстанавливает утерянный сентябрьский результат 24.5 → 52 → 65%.
2. **Self-play «не стартует».** Цель self-play — одноходовой Gumbel с C_VISIT=50, а гейты по 16–24 партии. Повторить с `--selfplay-full-mcts`: цели по посещениям, 400–800 sims, малый virtual batch, гейт 200 партий.
3. **Value по исходам движок-движок («5%»).** Повторить:
   - сплит по партиям, ≥100 тыс. независимых партий по реальному правилу;
   - отдельная value-сеть или голова без замораживания масштаба, цель ±1, а маржу — отдельной головой;
   - замер при batch 1.

   Ожидаем, что outcome-value из партий движка сильнее человеческой при достаточном объёме.
4. **Score/margin-голова (v4).** Внешний «ноль» был артефактом: исправленный счёт 45.8% против 29.2%. Пересыграть v4 и acc256 против production в одном окне. Для AZ: score-head как вспомогательная цель.
5. **Ширина аккумулятора.** С lr 5e-4 acc1024 по loss равна acc256. Стоит проверить acc512 или acc1024 с подобранным LR и большим числом данных/эпох при фиксированном **времени**: NPS падает в 3–4 раза, поэтому выигрыш маловероятен. Низкий приоритет.
6. **Данные PlayOK для NNUE.** Уже частично реабилитированы (mix1). Нужен чистый A/B: acc256 против acc256 + PlayOK-исходы (те же сиды, 3 сида) на эндшпильном наборе и в полных партиях.
7. **58 «стратегических» признаков.** Повторять в старом виде нет смысла: sparse-кодирование v2 уже кодирует точные счёты. Но вывод «явные признаки не нужны» не доказан. Можно добавить в v2 2–4 темповых признака (запас безопасных ходов, «запертые» камни) и мерить на эндшпильном наборе. Ручной темп-терм в оценке провалился (−116), но **признак, выученный сетью**, — другое дело.
8. **Ранние «законы» (batch, K, λ, объём данных).** Для нынешнего трейнера (BCE, NNUE v2) они вообще не переносятся. Если важно: 3 сида × 2 значения на эндшпильном наборе 480 партий, около 1 часа на точку.

## 7. Самый перспективный путь к 2500+ и обоснование

**Что на самом деле известно.**
- Единственный рычаг с положительным и воспроизводимым эффектом — **функция оценки, обученная на «правильных» метках**: win% сети 9qum, то есть дистилляция сильного AZ, плюс реальные исходы по реальному правилу при сплите по партиям.
  - In-lineage: +244 (acc256) и +64 сверху (mix1), по 480 партий, узкие ДИ.
  - Внешне: 41.7% против 12.5% и 40.9% против 8% при n=22–24 на руку.
- Всё, что «не сработало» в обучении, либо испорчено (эры 0/1, утечки, vb64, match.py, рассогласование признаков), либо мерилось на 16–50 партиях.
- Время ×4 даёт лишь +43 Elo на эндшпильном наборе, так что одной глубиной разрыв не закрыть.
- Существующие сильные программы (9qum, PlayOK `mcts` ≈2510) — семейство MCTS/AZ. По вторичным данным `mcts` выигрывает, держа камни на своей стороне: это ровно то, что учит value на исходах.
- 9qum «уровень I» — урезанная бесплатная версия (90 sims, mix 0.5, drop 0.25). 40% против неё не равно 2500. Абсолютный уровень mix1 сейчас **неизвестен**.

**Рекомендуемый путь** (две линии с общей инфраструктурой меток и гейтов):

0. **Сначала инфраструктура, 2–3 дня.** Без неё любой следующий вывод снова может оказаться ложным.
   - Влить в `main` только правило эры 2 вместе с EGTB02. Фатальная ошибка при отсутствии ассетов. Исправить match.py и ab_match.
   - Единый гейт: эндшпильный набор (240 позиций ×2) плюс полные партии (200 дебютов ×2) против **фиксированного** эталона (глубина 8 или 1 поток при фиксированных узлах), с ДИ.
   - Внешние парные гейты 9qum на 100+ партий в одном окне, обе руки чередуются, а не идут подряд.
   - Закоммитить `research/diag/*`.
1. **Линия A: NNUE v2 + итеративная outcome-разметка («AlphaZero для alpha-beta»).** Быстрая и измеримая.
   - (a) Чистый A/B: mix1 против mix2_acc256 против acc256, 3 сида каждый. mix2 ещё не сыграна.
   - (b) Генерация: лучший движок играет сам с собой по реальному правилу из позиций сильных человеческих партий (много стартов, от миттельшпиля до эндшпиля с 20–60 камнями), с небольшим шумом в ходах. Метка — исход и итоговая маржа, сплит по партиям, ≤12 позиций на партию.
   - (c) Обучение v2 на смеси «9qum-метки + человеческие исходы + свои исходы». Гейт против предыдущего поколения и против фиксированного эталона.

   Это переносит главную идею AlphaZero (value на исходах) в движок, который уже работает, и прямо бьёт по слабому месту — темповым эндшпилям с 20–40 камнями, где EGTB бесполезна. Сервер с 24 ядрами окупается здесь: миллионы доигрываний.

   Риск — потолок самодистилляции. Он смягчается якорем (человеческие исходы, метки 9qum) и гейтами против внешних эталонов.
2. **Линия B: AlphaZero/MCTS на сервере.** Потолок выше, поэтому запускать её стоит после пп. 6.1–6.3, когда известно, работает ли поиск.
   - Реальное правило; virtual batch ≤8 при оценке; цели self-play — посещения полного дерева (400–800 sims, а не 1-ply Gumbel).
   - Отдельная value-сеть или отдельная голова со score-head; value на исходах с game-level сплитом; старт value с данных линии A.
   - Гейты 200 партий.
   - **Точка остановки:** если за 7–10 дней ни один кандидат не прошёл честный гейт, а поиск при batch 1 не даёт прироста над policy, остановиться и разбирать value.

**Почему не только B.** Линия A уже дала единственный подтверждённый плюс, её цикл измеряется часами, и она производит данные (исходы по реальному правилу) для value в линии B.

**Почему не только A.** Внешние сильные соперники — AZ-семейство. Policy у нас самая слабая часть: совпадение 40.3% против 51.6% у 9qum. Alpha-beta с NNUE сам по себе выучить policy не может.

Ожидание силы — честно: доказательств, что любой из путей ведёт к 2500+, **нет**. Это лучшая ставка по имеющимся данным, а не прогноз.
